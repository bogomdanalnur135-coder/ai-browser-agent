# AI Browser Agent — Docker + REST API

Браузерный ИИ-агент запускается в контейнере и принимает задачи через HTTP API. Задачи асинхронные: API возвращает `task id`, затем можно проверять статус и результат. Для потенциально рискованных действий (отправка формы, регистрация, бронирование, оплата) агент останавливается и ждёт отдельного подтверждения через API.

## Что нужно

- Docker Desktop (Mac/Windows) или Docker Engine + Compose (Linux/VPS)
- Amazon Bedrock API key и ID модели/inference profile с поддержкой tool use (Converse API)

## Быстрый запуск на Mac

1. Распакуйте архив.
2. Можно дважды нажать `start.command`: при первом запуске он создаст `.env` и откроет его. Либо откройте Terminal в папке `ai-browser-agent`.
3. Создайте настройки:

   ```bash
   cp .env.example .env
   ```

4. Откройте `.env` в редакторе и замените `AWS_BEARER_TOKEN_BEDROCK`, `AWS_BEDROCK_MODEL_ID` и `API_TOKEN`. Для токена можно сгенерировать секрет командой `openssl rand -hex 32`.
5. Соберите и запустите контейнер:

   ```bash
   docker compose up --build -d
   ```

6. Проверьте состояние:

   ```bash
   docker compose ps
   curl http://localhost:8080/health
   ```

API по умолчанию доступен только с самого компьютера (`127.0.0.1`), чтобы не выставлять его в интернет без HTTPS и дополнительной настройки.

## Пример: отправить задачу

Подставьте свой `API_TOKEN` вместо `YOUR_API_TOKEN`:

```bash
curl -X POST http://localhost:8080/tasks \
  -H 'Authorization: Bearer YOUR_API_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Открой https://example.com и кратко опиши страницу"}'
```

Ответ `202 Accepted` содержит `task.id`. Проверяйте статус и результат:

```bash
curl http://localhost:8080/tasks/TASK_ID \
  -H 'Authorization: Bearer YOUR_API_TOKEN'
```

Статусы: `queued`, `running`, `awaiting_confirmation`, `completed`, `failed`, `cancelled`.

## Подтверждение бронирования / оплаты

Если статус `awaiting_confirmation`, ответ задачи покажет `approval` (текст действия, URL и предупреждение). Сначала проверьте эти данные и текущую страницу. Только если всё верно, явно разрешите действие:

```bash
curl -X POST http://localhost:8080/tasks/TASK_ID/confirm \
  -H 'Authorization: Bearer YOUR_API_TOKEN'
```

Чтобы запретить действие:

```bash
curl -X POST http://localhost:8080/tasks/TASK_ID/reject \
  -H 'Authorization: Bearer YOUR_API_TOKEN'
```

Отмена задачи:

```bash
curl -X POST http://localhost:8080/tasks/TASK_ID/cancel \
  -H 'Authorization: Bearer YOUR_API_TOKEN'
```

## Постоянная память

Агент хранит несекретные предпочтения и полезный контекст в `data/memory.json`; в Docker этот каталог сохраняется в отдельном volume `agent-data` между перезапусками. Модель может искать и добавлять записи через инструменты `memory_search` и `memory_save`. Можно добавить запись вручную через API:

```bash
curl -X POST http://localhost:8080/memory \\
  -H 'Authorization: Bearer YOUR_API_TOKEN' \\
  -H 'Content-Type: application/json' \\
  -d '{"text":"Предпочитаю краткие ответы на русском","tags":["предпочтения","язык"]}'
```

Посмотреть сохранённые записи: `GET /memory` с тем же заголовком авторизации. Не сохраняйте секреты, пароли, токены, платёжные данные или одноразовые коды.

## Быстродействие

В `.env` доступны `MAX_STEPS` (5–60, по умолчанию 30) и `PAGE_TEXT_LIMIT` (3000–20000 символов, по умолчанию 10000). Уменьшение лимита текста страницы и числа шагов может ускорить задачи и сократить расход токенов, но иногда снижает качество на сложных сайтах.

## Workflows: записать длинное действие и вызывать как API

Передайте `saveAsWorkflow` (и, при желании, `params`) в обычную задачу. Агент выполнит её сам, а успешные шаги
(`open_url`, `click_text`, `fill_field`) запишутся в `data/workflows.json`. Значения из `params` заменяются
плейсхолдерами `{{ключ}}`; сами значения остаются **значениями по умолчанию**.

```
curl -X POST http://localhost:8080/tasks -H 'Authorization: Bearer YOUR_API_TOKEN' -H 'Content-Type: application/json' \
  -d '{"prompt":"Оформи заказ ...","saveAsWorkflow":"order","params":{"email":"john@example.com","city":"Astana"}}'
```

Потом повторяйте без LLM — это асинхронная задача (`202` + `GET /tasks/:id`), как и обычные:

```
curl -X POST http://localhost:8080/workflows/order/run -H 'Authorization: Bearer YOUR_API_TOKEN' \
  -H 'Content-Type: application/json' -d '{"params":{"email":"mary@example.com","city":"Almaty"}}'
```

- Финальные действия (отправка формы, оплата и т.п.) тоже записываются с флагом `approval`: при повторе задача встаёт в
  `awaiting_confirmation` и ждёт `POST /tasks/:id/confirm` — без подтверждения такой шаг не выполняется. Если подтверждения нет
  `APPROVAL_TIMEOUT_MS`, шаг отклоняется.
- Каждый шаг ждёт свой элемент до `STEP_TIMEOUT_MS` (SPA, ленивый рендер). При ошибке задача получает `failed`,
  номер шага в тексте ошибки и скриншот в `data/failures/<task id>.png`.
- Если на шаге появилась проверка «вы человек», задача встаёт на ручной этап (noVNC) и после `/confirm` повторяет шаг.
- `GET /workflows`, `GET /workflows/:name` (шаги целиком), `DELETE /workflows/:name`.
- Значения `fill_field`, не заменённые параметрами, сохраняются как есть — не записывайте персональные данные без `params`.

## Память контейнера

`headless: false` памяти не добавляет (Xvfb и оконный Chromium потребляют больше). Реальные пределы задают Docker:
`mem_limit` / `shm_size` в `docker-compose.yml` (переопределяются `AGENT_MEM_LIMIT`, `AGENT_SHM_SIZE` в `.env`) и, на Mac/Windows,
общий лимит виртуальной машины Docker Desktop (Settings → Resources). Проверить, убивал ли контейнер OOM:
`docker inspect -f '{{.State.OOMKilled}}' ai-browser-agent-api`. Текущее потребление: `docker stats` и поле `rssMb` в `GET /health`.

## Проверки «я человек» / CAPTCHA

### Принцип работы

Агент не должен автоматически обходить CAPTCHA, Cloudflare Turnstile,
2FA или другие проверки человека. Если проверка появляется, задача должна
приостановиться со статусом `awaiting_confirmation`, чтобы пользователь
мог выполнить необходимое действие вручную.

### Важное ограничение Docker

Браузер запускается внутри Docker-контейнера и использует постоянный профиль
`browser-profile`. Запуск отдельного браузера на хосте с `HEADLESS=false`
не открывает браузер из контейнера и не гарантирует продолжение исходной задачи.

В текущей конфигурации Docker ещё не настроен графический дисплей и доступ
к нему через noVNC. Поэтому ручное прохождение CAPTCHA непосредственно
в браузере контейнера пока не считается настроенным.

### Планируемый сценарий ручного вмешательства

После настройки виртуального дисплея и защищённого доступа через noVNC:

1. Отправьте задачу через `POST /tasks`.
2. Проверяйте её статус через `GET /tasks/:id`.
3. При статусе `awaiting_confirmation` откройте предоставленный интерфейс
   браузера контейнера.
4. Самостоятельно пройдите проверку или выполните вход на сайте.
5. Убедитесь, что проверка завершена и страница готова продолжить работу.
6. Вызовите `POST /tasks/:id/confirm`, чтобы разрешить продолжение задачи.

Точные URL и порядок подтверждения должны соответствовать фактически
реализованному API. Не вызывайте подтверждение, пока ручное действие
не выполнено.

### Безопасность

- Не передавайте пароли, одноразовые коды и платёжные данные в промпте.
- Не публикуйте интерфейс noVNC или REST API в интернете без аутентификации
  и защищённого соединения.
- Не автоматизируйте обход антибот-защиты; используйте ручную проверку
  или официальный API сайта, если он доступен.
- Сохранение cookies и профиля не гарантирует, что сайт больше не запросит
  проверку.

## Остановка и логи

```bash
docker compose logs -f
docker compose down
```

Профиль браузера хранится в Docker volume `browser-profile` между перезапусками. Чтобы удалить его вместе с данными браузера: `docker compose down -v` (необратимо удалит volume).

## API

- `GET /health` — проверка работоспособности без авторизации
- `GET /` — список методов (требует токен)
- `POST /tasks` — создать задачу, JSON `{ "prompt": "..." }`
- `GET /tasks/:id` — статус, результат, логи и данные подтверждения
- `POST /tasks/:id/confirm` — разрешить ожидающее действие
- `POST /tasks/:id/reject` — отклонить ожидающее действие
- `POST /tasks/:id/cancel` — отменить задачу

## Важные ограничения

- Очередь выполняет по одной задаче за раз, так как используется один браузерный контекст.
- Список задач хранится в памяти процесса и очищается при пересоздании контейнера; это MVP, не production-хранилище.
- Контейнер работает в headless-режиме; видимого окна Chromium не будет. Профиль сохраняется в volume.
- Не передавайте в API пароли, платёжные данные, одноразовые коды или секреты. Пароли и платёжные поля агент не заполняет.
- CAPTCHA/2FA и другие проверки могут потребовать ручного вмешательства; агент не должен их обходить.
- Для размещения на VPS не публикуйте порт напрямую в интернет. Используйте HTTPS reverse proxy, firewall и секретный API token.
